## Purpose

Предоставить проверяемое описание HTTP API PostgreSQL-сервиса для независимой
разработки клиента без изменения действующего протокола.

## ADDED Requirements

### Requirement: Версионируемый контракт OpenAPI

Сервис SHALL поставлять контракт OpenAPI 3.1 в `openapi/stream-writer.v1.yaml` и
публиковать тот же документ в JSON на `GET /openapi.json`. Контракт SHALL
объявлять UUID в пути, типы тел, параметры, заголовки, формы ошибок и
стабильные `operationId`:

| Метод и маршрут | `operationId` |
| --- | --- |
| `PUT /v1/uploads/{upload_id}` | `uploadNdjson` |
| `GET /v1/uploads/{upload_id}` | `getUploadReceipt` |
| `GET /v1/uploads/{upload_id}/rows` | `listUploadRows` |
| `GET /v1/uploads/{upload_id}/rows/stream` | `streamUploadRows` |

Контракт SHALL описывать HTTP Bearer без требования JWT для всех четырёх
операций и для `/health/ready`. `/health/live` SHALL оставаться публичным.
Операции с UUID SHALL описывать `422` для некорректного UUID. Контракт MUST
сохранять действующие варианты JSON-ошибок: `detail` строкой для явного
отказа HTTP, массив элементов `detail` для ошибок валидации параметров и
`error`/`message` с `upload_id` для структурированных ошибок потоковой
обработки и PostgreSQL на маршрутах данных.

#### Scenario: Проверка контракта установленного сервера

- **WHEN** потребитель запрашивает `/openapi.json` у сервера, установленного из wheel или образа
- **THEN** сервер возвращает контракт OpenAPI 3.1 с теми же операциями, моделями и настройками авторизации, что и версия в репозитории

#### Scenario: Запрос без действующего токена

- **WHEN** клиент обращается к защищённому маршруту без действующего Bearer token
- **THEN** сервер возвращает `401`, заголовок `WWW-Authenticate: Bearer` и JSON с `detail` строкой

### Requirement: Контракт записи и квитанции

PUT SHALL принимать несжатые байты `application/x-ndjson`, по одному объекту
JSON в UTF-8 на строку. Успешные ответы PUT и GET квитанции SHALL содержать
`upload_id`, `sha256` исходных байтов, `row_count`, `byte_count`,
`committed_at` и `reused`. Успех PUT MUST означать подтверждённый commit.
Контракт SHALL описывать `400` для неверного потока или заголовка длины,
`408` для таймаута приёма, `409` для конфликта, `413` для лимитов,
`415` для неподдерживаемого типа, кодировки или сжатия, `422` для неверного UUID
и `503` для недоступности базы или неизвестного исхода commit.

#### Scenario: Запись и повтор исходного потока

- **WHEN** сервер фиксирует новый UUID либо получает подтверждённый UUID с теми же байтами
- **THEN** первая запись возвращает `201` и `reused=false`, повтор — `200` и `reused=true` без новых строк

#### Scenario: Конкурирующая запись или другие байты

- **WHEN** этот же UUID уже обрабатывается либо подтверждён с другими байтами
- **THEN** сервер возвращает соответственно `409 upload_in_progress` или `409 upload_conflict`

#### Scenario: Неизвестный исход записи

- **WHEN** клиент теряет ответ или получает `503 commit_unknown`
- **THEN** клиент может запросить квитанцию по исходному UUID; GET возвращает подтверждённую квитанцию или `404` в JSON с `detail` строкой
- **AND** такой `404` не доказывает, что ещё выполняющаяся запись уже отменена

### Requirement: Контракт страниц

GET страниц SHALL возвращать JSON для одной подтверждённой загрузки в порядке
возрастания `row_number`. Каждый элемент `rows` SHALL содержать
`row_number` и JSON-объект `data`; числовые значения JSONB SHALL сохранять
точность на уровне ответа. Контракт SHALL описывать `limit` от 1 до 1000
(по умолчанию 100), `offset` от 0 до `9223372036854775807` (по умолчанию 0 в
режиме offset) и `after_row_number` в том же диапазоне.

#### Scenario: Страница с курсором

- **WHEN** клиент передаёт только `after_row_number` как позицию
- **THEN** ответ включает `upload_id`, общий `row_count`, `limit`, `rows`, переданный `after_row_number` и `next_after_row_number`
- **AND** номера строк строго больше позиции; продолжение равно номеру последней строки страницы, если есть следующая страница, иначе равно `null`

#### Scenario: Совместимая страница offset

- **WHEN** клиент передаёт `offset` или не указывает ни одной позиции
- **THEN** ответ содержит `upload_id`, общий `row_count`, `limit`, `rows` и `offset` без полей курсора
- **AND** запрос за пределами результата возвращает `200` с пустым массивом

#### Scenario: Недопустимые параметры

- **WHEN** оба параметра позиции переданы вместе, даже с `offset=0`, либо один параметр некорректен
- **THEN** сервер возвращает `422` с `detail` строкой для конфликта параметров или массивом для ошибки их валидации

#### Scenario: Слишком большая страница

- **WHEN** для допустимого запроса JSON-ответ превышает 16 МиБ
- **THEN** сервер возвращает `413 page_too_large`

### Requirement: Контракт полной выгрузки

GET потока SHALL отдавать в порядке `row_number` сохранённые JSONB-объекты в
UTF-8 как последовательность строк `application/x-ndjson`. Одна строка
содержит `row_number` и `data`, завершается LF и сохраняет точность чисел.
Порция от приложения MUST быть не больше 128 КиБ, но получатель MUST NOT
полагаться на её границу. Успешная выгрузка SHALL содержать `X-Row-Count`
с числом ожидаемых строк. Страницы и поток SHALL возвращать
`Cache-Control: no-store`. SHA-256 квитанции относится к исходному PUT, а не
к экспортируемому NDJSON.

#### Scenario: Неизвестная загрузка

- **WHEN** клиент запрашивает страницу или поток неизвестной или ещё не подтверждённой загрузки
- **THEN** сервер возвращает JSON `404 upload_not_found`

#### Scenario: Сбой до начала ответа

- **WHEN** при подготовке потока база недоступна либо таймаут истекает до отправки заголовков
- **THEN** сервер возвращает JSON `503` с `database_unavailable` или `export_timeout` соответственно

#### Scenario: Ошибка или отмена после старта потока

- **WHEN** база выдаёт ошибку, истекает таймаут или клиент разрывает соединение после начала ответа
- **THEN** сервер освобождает соединение PostgreSQL и не завершает частичный поток как успешную выгрузку
- **AND** клиент не считает статус `200` достаточным: нужны штатное завершение тела и фактическое число строк, равное `X-Row-Count`

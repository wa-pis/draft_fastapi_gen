# Проверки Async PostgreSQL Writer

Локальная проверка: 2026-11-08, macOS ARM64, Python 3.13.14, PostgreSQL 14.20,
asyncpg 0.31.0. PostgreSQL запущен во временном каталоге, только с Unix-сокетом.

- 119 unit/fault-тестов парсера, API, конфигурации и CLI пройдены.
- 12 интеграционных тестов с настоящим PostgreSQL пройдены: COPY и receipt в одной
  транзакции, отсутствие частичной видимости, повтор, конфликт, параллельный UUID,
  отмена, обрыв источника, переполнение пула, timeout и отказ JSONB.
- Реальный COMMIT с последующей искусственной потерей ответа проверен через fault
  injection на границе транзакции. GET видит receipt, повтор не создаёт дубликаты.
  Это не тест сетевого разделения или failover PostgreSQL.
- Ruff check/format, строгая валидация OpenSpec и проверка diff пройдены.
- Wheel и sdist собраны; wheel установлен с зависимостями в чистое временное
  окружение. Проверены установленная команда, packaged schema.sql и init-db.
- Установленное приложение проверено через настоящий Uvicorn/HTTP и PostgreSQL:
  поток 34 045 952 байта, 32 768 JSON-объектов, 0,574 с на первый PUT.
  Проверены GET, точный повтор, конфликт, поздняя ошибка JSON и обрыв HTTP-сокета.
  В БД осталось 32 768 строк успешной загрузки, для обоих сбоев — 0.
  Максимальный RSS дочерних процессов на macOS — 69 074 944 байта.

Данные smoke-теста повторяются и хорошо сжимаются; это функциональная проверка,
не прогноз скорости, размера БД или памяти на реальных результатах калькуляции.
Проверки 1 и 5 ГиБ приведены ниже. TLS, репликация, crash recovery и нагрузка целевой
БД не проверены.

На момент этой проверки Docker и Compose были недоступны. GitHub Actions проверил
PostgreSQL 17, wheel, сборку Docker и команду в образе; итог запуска — в
[PR #17](https://github.com/wa-pis/draft_fastapi_gen/pull/17). Позднее полный стенд был
проверен отдельно: [Docker Compose и PostgreSQL 17](#docker-compose-и-postgresql-17).

## Потоковая запись 1 и 5 ГиБ

2026-11-08: Apple M4 Max, 14 CPU, 36 ГиБ RAM, macOS 26.6.2, Python 3.13.14,
PostgreSQL 14.20, asyncpg 0.31.0. Проверен код сервиса из main `4c31eda`:
отдельный процесс установленного wheel, настоящий HTTP/Uvicorn и PostgreSQL через
локальный Unix-сокет. Для каждого итогового прогона создана новая пустая база.

Вход — ровно 1/5 ГиБ NDJSON, строки по 4 096 байт, включая JSON и LF. Payload каждой
строки различается: детерминированные случайные байты преобразованы в base64-алфавит.
Клиент передаёт порции по 64 КиБ; полного файла на диске или в памяти нет.
Таймер записи включает генерацию, SHA-256, HTTP, COPY и подтверждение commit.

| Вход | Строк | Запись | Скорость входа | Полное чтение | Повтор PUT |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 ГиБ | 262 144 | 19,598 с | 52,249 МиБ/с | 4,734 с | 5,674 с |
| 5 ГиБ | 1 310 720 | 137,909 с | 37,126 МиБ/с | 24,009 с | 29,654 с |

| Вход | RSS API | RSS клиента | RSS одного API-backend PostgreSQL | Таблица + TOAST + индексы | Сгенерированный WAL |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 ГиБ | 69,55 МиБ | 57,39 МиБ | 152,45 МиБ | 1,379 ГиБ | 1,137 ГиБ |
| 5 ГиБ | 69,75 МиБ | 55,95 МиБ | 163,83 МиБ | 6,894 ГиБ | 5,687 ГиБ |

RSS — максимальные выборки каждые 0,5 с на этапах записи, чтения и повтора; короткий
пик мог быть пропущен. RSS backend PostgreSQL включает общие страницы и не показывает
всю память кластера. WAL — разность LSN первого PUT, а не размер каталога `pg_wal`.

Для обоих объёмов подтверждено:

- HTTP 201, точные счётчики байтов/строк и SHA-256 receipt; GET возвращает тот же receipt.
- Прочитана **каждая** строка через cursor с prefetch 256: последовательные номера,
  точный набор полей и SHA-256 восстановленного NDJSON совпали с входом.
- Повторный полный PUT с тем же UUID вернул 200 и `reused=true`; receipt и timestamp
  сохранены, число строк в PostgreSQL не изменилось.
- После штатного перезапуска PostgreSQL и API GET вернул прежний receipt, число строк
  в БД совпало. Это не имитация потери питания или failover.
- После проверки отдельные нагрузочные базы удалены, процесс PostgreSQL остановлен.

`fsync=on`, `synchronous_commit=on`, `full_page_writes=on`, shared_buffers 128 МиБ,
max_wal_size 1 ГиБ, checkpoint_timeout 300 с, wal_compression и data_checksums выключены.
Настройки БД не менялись ради результата. Кеш ОС не очищался. Генератор, API и PostgreSQL
делят одну машину, поэтому это локальная сквозная скорость, а не предел PostgreSQL.
Скорость на 5 ГиБ ниже. Во время этого PUT PostgreSQL сообщал о частых checkpoint
с интервалами 10–15 с и предлагал увеличить max_wal_size. Это наблюдение для дальнейшего
профилирования, а не доказанная причина снижения скорости. Это одиночные итоговые
замеры, без статистики задержек или параллельной нагрузки.

Скрипт и инструкции: [benchmarks/README.md](benchmarks/README.md). Исходные результаты:
[1 ГиБ](benchmarks/results/2026-11-08-1gib.json),
[5 ГиБ](benchmarks/results/2026-11-08-5gib.json). Эти результаты не заменяют приёмку
на целевой версии PostgreSQL, с TLS, репликами, реальной схемой и данными калькуляции.

## Оптимизация потока 5 ГиБ

2026-11-09: тот же локальный стенд PostgreSQL 14.20/macOS ARM64, Apple M4 Max,
36 ГиБ RAM, Python 3.13.14. Настройки менялись по одному фактору. Каждый прогон
использовал новую пустую базу, новый процесс API и явный CHECKPOINT перед таймером.
Вход, SHA-256 и схема совпадают с предыдущим тестом; 5 ГиБ — 1 310 720 строк.
Во всех профилях shared_buffers 128 МиБ, checkpoint_timeout 300 с,
checkpoint_completion_target 0,9, fsync/full_page_writes/synchronous_commit включены.
В этой серии включены track_io_timing и track_wal_io_timing, поэтому абсолютное время
не следует напрямую сравнивать с серией 2026-11-08. Файловый кеш ОС не очищался.

| Прогон | Вход | Parser | max_wal_size / wal_buffers | Запись | Скорость входа | Повтор PUT |
| --- | ---: | --- | --- | ---: | ---: | ---: |
| [A](benchmarks/results/2026-11-09-baseline-a-5gib.json) | 5 ГиБ | исходный | 1 ГиБ / 4 МиБ | 170,371 с | 30,052 МиБ/с | 29,363 с |
| [B](benchmarks/results/2026-11-09-wal8-only-b-5gib.json) | 5 ГиБ | исходный | 8 ГиБ / 4 МиБ | 133,426 с | 38,373 МиБ/с | 28,802 с |
| [C](benchmarks/results/2026-11-09-walbuffers16-c-5gib.json) | 5 ГиБ | исходный | 8 ГиБ / 16 МиБ | 74,391 с | 68,826 МиБ/с | 29,049 с |
| [F](benchmarks/results/2026-11-09-optimized-f-repeat-5gib.json) | 5 ГиБ | быстрый | 8 ГиБ / 16 МиБ | 64,762 с | 79,059 МиБ/с | 15,306 с |
| [E](benchmarks/results/2026-11-09-optimized-e-1gib.json) | 1 ГиБ | быстрый | 8 ГиБ / 16 МиБ | 13,973 с | 73,282 МиБ/с | 2,872 с |

В этой серии итоговые 5 ГиБ быстрее A в 2,63 раза; снижения скорости относительно
итоговых 1 ГиБ не наблюдалось. Это отдельные последовательные прогоны, а не средние
значения или доверительные интервалы. Случайный payload, локальный диск, кеш и
конкуренция за одну машину ограничивают переносимость результата.

### Что ограничивало запись

- В A 203 из 335 наблюдений API-backend были `active / IO / WALWrite` — около 61%.
  Число запрошенных checkpoint в окне наблюдения A/B снизилось с 11 до 1 при
  увеличении max_wal_size. Это согласуется с дополнительной нагрузкой от частых
  checkpoint. Объём сгенерированного WAL почти не изменился — около 5,69 ГиБ.
- Увеличение wal_buffers отдельно от max_wal_size (B → C) уменьшило
  `wal_buffers_full` с 576 839 до 148 489, `wal_write` с 577 674 до 149 019,
  `wal_write_time` с 78,226 до 21,288 с. Это подтверждает пользу большего буфера
  WAL на этом стенде. В F число WAL writes — 209 007, время — 24,743 с:
  давление WAL снизилось, но запись журнала остаётся заметной работой.
- В Python каждая строка проходила regex-поиск NUL и суррогатов. Для ASCII теперь
  используется быстрая проверка NUL и `isascii()`, для остальных строк сохраняется
  исходный поиск. Ошибочные строки, ключи, Unicode, digest и счётчики проверены
  регрессионными тестами. Разницу C → F нельзя полностью приписать парсеру из-за
  разброса I/O; повтор PUT, который проверяет поток без нового COPY, ускорился
  с 29,049 до 15,306 с.

Счётчики WAL/bgwriter относятся ко всему кластеру и включают фоновую работу.
Их окно шире HTTP PUT: подключение/остановка монитора и пауза публикации статистики.
Времена WAL/checkpoint нельзя складывать как независимые части времени запроса;
checkpoint_write_time включает намеренно растянутую фоновую запись.
Наблюдение `active / none / none` само по себе не доказывает загрузку CPU.
`wal_sync=0` здесь не означает отсутствие синхронизации: используется
`wal_sync_method=open_datasync`. Метод синхронизации не менялся ради ускорения.
В исходных замерах 2026-11-08 этих счётчиков не было: точную долю причин старого
разрыва 1/5 ГиБ восстановить нельзя.

### Проверка замеров и результата

Прогон [D](benchmarks/results/2026-11-09-optimized-d-5gib.json) исключён из сравнения
производительности: клиентский таймер показал 69,244 с, PostgreSQL — 245,004 с
активного времени и 205,145 с WAL I/O. Данные прошли проверку, но причина расхождения
длительностей не установлена; значения не корректировались. На macOS часы Python
и PostgreSQL могут по-разному учитывать системный сон
([Apple](https://developer.apple.com/documentation/kernel/1646199-mach_continuous_time?language=objc),
[PG14 timer](https://github.com/postgres/postgres/blob/REL_14_20/src/include/portability/instr_time.h));
это возможное объяснение, а не доказательство события D.

F повторён с `caffeinate -i` и сопоставлением двух таймеров: обычный — 64,762977 с,
монотонный — 64,761865 с, разница 0,001112 с. Активное время БД — 64,785 с.
Полнота activity-monitor B/C/D/E/F — complete, без timeout/ошибок. Первый неудачный
запуск B завершился HTTP 201, но ошибка диагностического монитора прервала дальнейшую
проверку; он не включён в результаты. Обработка ошибок монитора исправлена перед
повтором B. Версии диагностической обвязки и их границы описаны в
[benchmarks/README.md](benchmarks/README.md#диагностика).

SHA-256 исходников в JSON относятся к файлам, исполненным во время замеров,
до добавления поясняющих комментариев; алгоритм после замеров не менялся.

Для всех шести сохранённых прогонов проверены receipt/GET, полное чтение **каждой**
строки с проверкой общего SHA-256, полный повтор PUT без дубликатов, receipt и число строк после
штатного перезапуска PostgreSQL/API. Итоговый RSS API: 70,03 МиБ на 1 ГиБ и
70,81 МиБ на 5 ГиБ; на 5 ГиБ клиент — 58,17 МиБ, отдельный backend — 176,77 МиБ.
Это выборки раз в 0,5 с, а не гарантия максимума памяти. Схема, индексы, FK,
одна транзакция и гарантии commit сохранены. Нагрузочные базы удалены,
временный PostgreSQL остановлен.

После изменений прошли 137 unit/fault-тестов и 12 тестов с настоящим PostgreSQL,
Ruff check/format, строгая валидация OpenSpec и проверка diff. В runtime не добавлены
зависимости. Эта серия выполнена без Compose; контейнерный прогон приведён ниже.

Опциональный [compose.bulk.yaml](compose.bulk.yaml) задаёт 8 ГиБ WAL и буфер 16 МиБ.
Для внешнего PostgreSQL параметры задаёт администратор; приложение их не меняет.
Больший max_wal_size требует дискового запаса и может увеличить crash recovery;
это мягкий предел, а реплики/архиватор могут удерживать дополнительный WAL.
Основание: [bulk loading](https://www.postgresql.org/docs/14/populate.html#POPULATE-MAX-WAL-SIZE),
[WAL configuration](https://www.postgresql.org/docs/14/wal-configuration.html) и
[параметры WAL](https://www.postgresql.org/docs/14/runtime-config-wal.html).
Реальные результаты калькуляции, TLS, репликация, одновременные загрузки и аварийное
восстановление требуют проверки на целевом стенде.

## Docker Compose и PostgreSQL 17

2026-11-09: PostgreSQL 17.11 и приложение из `main` (`3580d8d`) работали в Docker
Compose 5.7.0 в VM Colima 0.9.1 (Linux ARM64, 6 CPU, 8 ГиБ RAM, диск 45 ГиБ).
Генератор остался на том же Mac M4 Max (Python 3.13.14) и обращался к приложению
по опубликованному порту. В образе API — Python 3.13.18. Для каждого объёма использован отдельный Compose-проект
с новым именованным томом; версии и идентификаторы образов записаны в JSON.

Профиль WAL как в оптимизированных замерах E/F: `max_wal_size=8GB`,
`wal_buffers=16MB`, `shared_buffers=128MB`, оба I/O timing и гарантии записи включены.
Перед таймером выполнялся `CHECKPOINT`. Вход, SHA-256, размер порций и таймер первого
PUT до подтверждения commit совпадают с методикой нативных замеров. RSS измерялся
только для клиента: PID контейнеров Linux недоступны локальному `ps` на Mac.

| Вход | PG14 до оптимизации | PG14 с оптимизацией | PG17 в Compose | Ускорение к оптимизированному PG14 |
| --- | ---: | ---: | ---: | ---: |
| 1 ГиБ | 19,598 с / 52,249 МиБ/с | 13,973 с / 73,282 МиБ/с | **6,040 с / 169,543 МиБ/с** | 2,31× |
| 5 ГиБ | 137,909 с / 37,126 МиБ/с | 64,762 с / 79,059 МиБ/с | **30,365 с / 168,615 МиБ/с** | 2,13× |

Скорость записи 5 ГиБ ниже скорости 1 ГиБ всего на 0,55% в этом тесте. При этом
полное чтение заняло 6,767/37,552 с на 1/5 ГиБ против 4,932/24,985 с нативно;
повтор PUT — 4,336/20,866 с против 2,872/15,306 с. Ускорилась именно первая запись.

Объём WAL на 5 ГиБ практически тот же (5,687 ГиБ). PostgreSQL 17 в VM использовал
`fdatasync`: `wal_write_time` — 1,135 с, `wal_sync_time` — 2,135 с; нативный
PostgreSQL 14 с `open_datasync` показал 24,743 с в `wal_write_time`, куда входит
синхронизация этим методом. Счётчики относятся ко всему кластеру и не выделяют
время COMMIT. Сравниваются два стенда: вместе с версией PostgreSQL изменились ОС,
сетевой путь, хранилище и метод синхронизации. Замеры не выделяют эффект версии.

Для обоих объёмов прочитаны все строки, общий SHA-256 совпал с нативными прогонами,
повтор не создал дубликатов, receipt и число строк сохранились после штатного
перезапуска PostgreSQL и API. Разница обычного и монотонного таймеров меньше 0,4 мс.
На 5 ГиБ минимальный запас места составил 28,09 ГиБ в VM и 40,13 ГиБ на Mac.
Первый пробный PUT 1 ГиБ занял 6,234 с и прошёл чтение и повтор, но не вошёл в
таблицу: клиент пытался проверить рестарт по прежним случайным портам. Полный
прогон повторён на новом томе с определением портов после перезапуска. Тестовые тома
и профиль Colima удалены. SHA-256 скрипта в JSON фиксирует файл до форматирования;
после замеров код прошёл проверку на эквивалентность Python AST.

Исходные отчёты: [1 ГиБ](benchmarks/results/2026-11-09-compose-pg17-1gib.json),
[5 ГиБ](benchmarks/results/2026-11-09-compose-pg17-5gib.json).
[Как повторить](benchmarks/README.md#через-docker-compose-с-postgresql-17).
Это по одному полному прогону на объём. Одновременные загрузки проверены ниже.

## Одновременные загрузки 5 ГиБ в PostgreSQL 17

Для каждого сценария использован отдельный проект Docker Compose с пустым томом.
PostgreSQL 17.11 — тот же образ, что в одиночном замере; код сервиса, настройки WAL
и гарантии записи совпадают. Перед каждым замером выполнялся `CHECKPOINT`. В VM
Colima оставили 6 CPU и 8 ГиБ RAM, виртуальный диск увеличили с 45 до 85 ГиБ.
Пул сервиса — четыре соединения.
Один клиент на том же Mac генерировал NDJSON по 5 ГиБ на запрос и отправлял PUT с
разными UUID. Время группы — от запуска PUT до последнего ответа с подтверждением
COMMIT; чтение и повторы в таймер не входят.

| Сценарий | Общий вход | Время группы | Суммарная скорость | Скорость одного PUT |
| --- | ---: | ---: | ---: | ---: |
| [1×5 ГиБ, прежний замер](benchmarks/results/2026-11-09-compose-pg17-5gib.json) | 5 ГиБ | 30,365 с | 168,615 МиБ/с | 168,615 МиБ/с |
| [2×5 ГиБ](benchmarks/results/2026-11-09-compose-pg17-2x5gib.json) | 10 ГиБ | 73,569 с | 139,189 МиБ/с | 69,595–69,827 МиБ/с |
| [4×5 ГиБ](benchmarks/results/2026-11-09-compose-pg17-4x5gib.json) | 20 ГиБ | 124,837 с | 164,054 МиБ/с | 41,014–41,030 МиБ/с |

Суммарная скорость ниже одиночной на 17,45% при двух загрузках и на 2,70% при
четырёх. Четыре потока дали на 17,86% больше суммарной скорости, чем два, но
отдельный PUT занял 124,785–124,837 с против 73,324–73,569 с при двух потоках.
Монитор PostgreSQL видел два одновременных `COPY` в 144 из 146 замеров и четыре —
в 246 из 247. В обоих параллельных прогонах чаще наблюдались ожидания `WALWrite`
и `extend` при расширении файлов таблицы. Клиент использовал в среднем 62% одного
ядра в обоих прогонах. Эти наблюдения не устанавливают, какой ресурс ограничил
скорость. По одному прогону на сценарий нельзя отделить разницу в 2,70% от разброса
между запусками.

Прочитаны все 30 ГиБ (7 864 320 строк), SHA-256 каждой загрузки совпал с исходным
потоком. Повтор PUT с тем же UUID не добавил строк. После штатного перезапуска
PostgreSQL и API повторно проверены все подтверждения и число строк по каждому UUID.
Таблица с TOAST и индексами заняла 13,82/27,64 ГиБ при двух/четырёх потоках,
сгенерировано 11,41/22,86 ГиБ WAL. На четырёх потоках осталось минимум 19,61 ГиБ
на Mac и 42,17 ГиБ в VM. Тестовые тома и профиль VM удалены.

[Как повторить](benchmarks/README.md#два-и-четыре-одновременных-потока-по-5-гиб).

## Повтор параллельных замеров и настройка WAL-буфера

В исходных прогонах доля активных наблюдений `LWLock/WALWrite` росла с 3,3% до
14,5% и 22,2% при одном, двух и четырёх потоках. `Lock/extend` рос с 0% до 13,8%
и 22,2%. Эти доли считаются по наблюдениям каждого backend, а не по времени всей
группы. При четырёх потоках запрошено больше checkpoint (5 против 2 при двух);
на ГиБ входа суммарное время записи и синхронизации WAL тоже выше. Старые прогоны
показывают конкуренцию за WAL и файлы таблиц, но не выделяют причину провала на двух
потоках.

2026-11-10: повтор на PostgreSQL 17.11 в одной VM Colima (6 CPU, 8 ГиБ RAM,
диск 85 ГиБ), тот же образ PostgreSQL, один образ сервиса и пул из четырёх соединений.
Каждый прогон использовал свежий том, тот же генератор с 5 ГиБ на PUT и `CHECKPOINT`
перед замером. Между профилями менялся только `wal_buffers`: 16 МиБ (A) и 64 МиБ
(B). `max_wal_size=8GB`, `fsync`, `full_page_writes` и `synchronous_commit` оставлены
без изменений. PostgreSQL сохраняет прежние гарантии при увеличении буфера; эта
настройка задаёт объём памяти для WAL и применяется при запуске сервера.
[Документация PostgreSQL 17 о WAL](https://www.postgresql.org/docs/17/wal-configuration.html).

| Сценарий | 16 МиБ: время / суммарная скорость | 64 МиБ: время / суммарная скорость | Изменение скорости |
| --- | ---: | ---: | ---: |
| 1 × 5 ГиБ, контроль | 27,605 с / 185,476 МиБ/с | — | — |
| 2 × 5 ГиБ, первая пара (A → B) | 50,207 с / 203,954 МиБ/с | 44,659 с / 229,296 МиБ/с | +12,43% |
| 2 × 5 ГиБ, вторая пара (B → A) | 50,063 с / 204,544 МиБ/с | 47,298 с / 216,501 МиБ/с | +5,85% |
| 4 × 5 ГиБ, одна пара (B → A) | 98,134 с / 208,695 МиБ/с | 91,848 с / 222,976 МиБ/с | +6,84% |

Провал при двух потоках не повторился: даже с 16 МиБ оба замера на двух потоках
обогнали одиночный контроль. Четыре потока с теми же настройками дали на 2,2% больше
суммарной скорости, чем среднее двух повторов на двух потоках. На тех же 10 ГиБ
первый новый прогон использовал 29,48 с процессорного времени клиента против 45,52 с
в старом, а время синхронизации WAL изменилось с 6,92 до 5,65 с. По этим счётчикам
нельзя установить причину различия между сериями или отнести его к одному ресурсу.

При двух потоках средняя скорость двух прогонов выросла с 204,25 до 222,90 МиБ/с
(+9,13%). `wal_buffers_full` снизился с 786–791 тыс. до 54–61 тыс. на 10 ГиБ; при
четырёх потоках — с 1,61 млн до 45 тыс. на 20 ГиБ. Объём WAL почти не изменился,
число запросов на checkpoint сохранилось (2 при двух и 5 при четырёх потоках).
Изменение согласуется с меньшим количеством вынужденных записей при заполнении
буфера. Осталась конкуренция за расширение TOAST: в обоих прогонах на четырёх
потоках все ожидания расширения, для которых отдельная выборка `pg_locks` успела
определить таблицу, пришлись на TOAST. С четырьмя потоками суммарная скорость
с буфером 64 МиБ почти та же, что в среднем с двумя, а отдельный PUT дольше ждёт
ответа: около 92 с вместо 45–47 с. Это измерение на синтетических данных и одном
стенде; для четырёх потоков проверена одна пара.

Пары A/B проверяли подтверждения и число строк по каждому UUID. Отдельный прогон
2 × 5 ГиБ с 64 МиБ занял 46,109 с (222,082 МиБ/с): все 10 ГиБ вычитаны, оба SHA-256
совпали, повтор не добавил строк, после штатного перезапуска сохранились
подтверждения и 2 621 440 строк. Этот прогон не включён в среднее двух пар. Две
незавершённые попытки исключены: до старта не набрался заданный запас места на хосте,
а в другой измерение каталога `pg_wal` прервалось при переименовании сегмента.
Оба сценария повторены на пустых томах.

## 25 колонок против JSONB в Docker Compose

На том же локальном стенде PostgreSQL 17.11 сравнили две обычные журналируемые
таблицы с PK `(upload_id, row_number)` и FK на квитанцию. В каждом сценарии
использовался свежий том, `CHECKPOINT` перед стартом и четыре соединения в пуле.
`wal_buffers=64MB`, `max_wal_size=8GB`, `fsync=on`, `full_page_writes=on` и
`synchronous_commit=on`. HTTP 201 возвращался после коммита строк и квитанции
в одной транзакции на запрос. Обе таблицы заполнялись двоичным COPY.

Контроль JSONB получил тот же NDJSON, что и вариант с колонками: 4 096 байт на
строку, 1 310 720 строк и 5 368 709 120 байт на PUT. Для каждого уровня
параллельности совпадают UUID, байты и SHA-256 загрузок. Вариант с колонками
сохраняет большие псевдослучайные значения в `description` или в `metrics.note`
вместо общего JSONB. Исторические замеры JSONB с двумя полями не входят в это
сравнение.

| Загрузки | JSONB: время / скорость | 25 колонок: время / скорость | Изменение скорости |
| --- | ---: | ---: | ---: |
| 2 × 5 ГиБ | 70,078 с / 146,124 МиБ/с | 121,084 с / 84,569 МиБ/с | −42,1% |
| 4 × 5 ГиБ | 127,608 с / 160,492 МиБ/с | 253,758 с / 80,707 МиБ/с | −49,7% |

Скорость суммарная, до последнего HTTP 201. В варианте с колонками переход с двух
потоков на четыре не дал ускорения. Зато таблица с индексами и TOAST заняла примерно
на 20% меньше места: на четырёх потоках 22,23 ГиБ вместо 27,68 ГиБ. Объём
сгенерированного WAL уменьшился примерно на 14% в обеих парах; на четырёх
потоках — с 23,53 до 20,29 ГиБ. Из 22,23 ГиБ типизированной таблицы 20,22 ГиБ
всё ещё заняли TOAST и его индекс.

На четырёх потоках `ClientRead` составил 87,1% активных наблюдений у варианта
с колонками против 30,3% у JSONB. По трём снимкам Docker HTTP-сервис в обоих
режимах использовал примерно одно ядро, а PostgreSQL — 0,41–0,49 ядра с колонками
против 2,06–2,28 ядра с JSONB. Это согласуется с ограничением на стороне сервиса:
текущий прототип повторно разбирает JSON после общей проверки NDJSON, преобразует
поля и передаёт 25 значений драйверу. Вклад отдельных операций не измерялся.
Монитор зафиксировал `Lock/extend` 60 раз у JSONB и ни разу у типизированного
варианта. В этой серии монитор не определял отношение для этих ожиданий; меньшая
скорость подачи строк тоже могла снизить конкуренцию.

Во всех четырёх сценариях совпали SHA-256 входа и число строк по каждому UUID.
После штатного перезапуска совпали квитанции, количество и диапазон номеров
строк, а также значения всех полей первых 32 строк на загрузку. Полное чтение
и повтор без дублей прошли в отдельных небольших прогонах на обоих вариантах.
Интеграционный тест подтвердил, что ошибка типизации откатывает и строки, и квитанцию.
Это один локальный прогон на сценарий с синтетическими строками 4 КиБ; цифры
характеризуют весь путь HTTP → COPY → commit, включая работу Python, и не
измеряют чистую производительность PostgreSQL.

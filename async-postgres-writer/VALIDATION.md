# Проверки Async PostgreSQL Writer

Локальная проверка: 2026-11-08, macOS ARM64, Python 3.13.14, PostgreSQL 14.20,
asyncpg 0.31.0. PostgreSQL запущен во временном каталоге, только с Unix-сокетом.

- 119 unit/fault-тестов парсера, API, конфигурации и CLI пройдены.
- 12 интеграционных тестов с настоящим PostgreSQL пройдены: COPY и receipt в одной
  транзакции, отсутствие частичной видимости, повтор, конфликт, параллельный UUID,
  отмена, обрыв источника, переполнение пула, timeout и отказ JSONB.
- Реальный COMMIT с последующей искусственной потерей ответа проверен через fault
  injection на границе транзакции. GET видит receipt, повтор не создаёт дубликаты.
  Это не тест сетевого разделения или failover PostgreSQL.
- Ruff check/format, строгая валидация OpenSpec и проверка diff пройдены.
- Wheel и sdist собраны; wheel установлен с зависимостями в чистое временное
  окружение. Проверены установленная команда, packaged schema.sql и init-db.
- Установленное приложение проверено через настоящий Uvicorn/HTTP и PostgreSQL:
  поток 34 045 952 байта, 32 768 JSON-объектов, 0,574 с на первый PUT.
  Проверены GET, точный повтор, конфликт, поздняя ошибка JSON и обрыв HTTP-сокета.
  В БД осталось 32 768 строк успешной загрузки, для обоих сбоев — 0.
  Максимальный RSS дочерних процессов на macOS — 69 074 944 байта.

Данные smoke-теста повторяются и хорошо сжимаются; это функциональная проверка,
не прогноз скорости, размера БД или памяти на реальных результатах калькуляции.
Проверки 1 и 5 ГиБ приведены ниже. TLS, репликация, crash recovery и нагрузка целевой
БД не проверены.

Локальный Docker daemon и Compose недоступны, поэтому локальная сборка/запуск образа
не выполнены. GitHub Actions проверяет PostgreSQL 17, wheel, сборку Docker и команду
в образе; итог запуска смотрите в [PR #17](https://github.com/wa-pis/draft_fastapi_gen/pull/17). Полный запуск Compose требует
отдельной проверки.

## Потоковая запись 1 и 5 ГиБ

2026-11-08: Apple M4 Max, 14 CPU, 36 ГиБ RAM, macOS 26.6.2, Python 3.13.14,
PostgreSQL 14.20, asyncpg 0.31.0. Проверен код сервиса из main `4c31eda`:
отдельный процесс установленного wheel, настоящий HTTP/Uvicorn и PostgreSQL через
локальный Unix-сокет. Для каждого итогового прогона создана новая пустая база.

Вход — ровно 1/5 ГиБ NDJSON, строки по 4 096 байт, включая JSON и LF. Payload каждой
строки различается: детерминированные случайные байты преобразованы в base64-алфавит.
Клиент передаёт порции по 64 КиБ; полного файла на диске или в памяти нет.
Таймер записи включает генерацию, SHA-256, HTTP, COPY и подтверждение commit.

| Вход | Строк | Запись | Скорость входа | Полное чтение | Повтор PUT |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 ГиБ | 262 144 | 19,598 с | 52,249 МиБ/с | 4,734 с | 5,674 с |
| 5 ГиБ | 1 310 720 | 137,909 с | 37,126 МиБ/с | 24,009 с | 29,654 с |

| Вход | RSS API | RSS клиента | RSS одного API-backend PostgreSQL | Таблица + TOAST + индексы | Сгенерированный WAL |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 ГиБ | 69,55 МиБ | 57,39 МиБ | 152,45 МиБ | 1,379 ГиБ | 1,137 ГиБ |
| 5 ГиБ | 69,75 МиБ | 55,95 МиБ | 163,83 МиБ | 6,894 ГиБ | 5,687 ГиБ |

RSS — максимальные выборки каждые 0,5 с на этапах записи, чтения и повтора; короткий
пик мог быть пропущен. RSS backend PostgreSQL включает общие страницы и не показывает
всю память кластера. WAL — разность LSN первого PUT, а не размер каталога `pg_wal`.

Для обоих объёмов подтверждено:

- HTTP 201, точные счётчики байтов/строк и SHA-256 receipt; GET возвращает тот же receipt.
- Прочитана **каждая** строка через cursor с prefetch 256: последовательные номера,
  точный набор полей и SHA-256 восстановленного NDJSON совпали с входом.
- Повторный полный PUT с тем же UUID вернул 200 и `reused=true`; receipt и timestamp
  сохранены, число строк в PostgreSQL не изменилось.
- После штатного перезапуска PostgreSQL и API GET вернул прежний receipt, число строк
  в БД совпало. Это не имитация потери питания или failover.
- После проверки отдельные нагрузочные базы удалены, процесс PostgreSQL остановлен.

`fsync=on`, `synchronous_commit=on`, `full_page_writes=on`, shared_buffers 128 МиБ,
max_wal_size 1 ГиБ, checkpoint_timeout 300 с, wal_compression и data_checksums выключены.
Настройки БД не менялись ради результата. Кеш ОС не очищался. Генератор, API и PostgreSQL
делят одну машину, поэтому это локальная сквозная скорость, а не предел PostgreSQL.
Скорость на 5 ГиБ ниже. Во время этого PUT PostgreSQL сообщал о частых checkpoint
с интервалами 10–15 с и предлагал увеличить max_wal_size. Это наблюдение для дальнейшего
профилирования, а не доказанная причина снижения скорости. Это одиночные итоговые
замеры, без статистики задержек или параллельной нагрузки.

Скрипт и инструкции: [benchmarks/README.md](benchmarks/README.md). Исходные результаты:
[1 ГиБ](benchmarks/results/2026-11-08-1gib.json),
[5 ГиБ](benchmarks/results/2026-11-08-5gib.json). Эти результаты не заменяют приёмку
на целевой версии PostgreSQL, с TLS, репликами, реальной схемой и данными калькуляции.

## Оптимизация потока 5 ГиБ

2026-11-09: тот же локальный стенд PostgreSQL 14.20/macOS ARM64, Apple M4 Max,
36 ГиБ RAM, Python 3.13.14. Настройки менялись по одному фактору. Каждый прогон
использовал новую пустую базу, новый процесс API и явный CHECKPOINT перед таймером.
Вход, SHA-256 и схема совпадают с предыдущим тестом; 5 ГиБ — 1 310 720 строк.
Во всех профилях shared_buffers 128 МиБ, checkpoint_timeout 300 с,
checkpoint_completion_target 0,9, fsync/full_page_writes/synchronous_commit включены.
В этой серии включены track_io_timing и track_wal_io_timing, поэтому абсолютное время
не следует напрямую сравнивать с серией 2026-11-08. Файловый кеш ОС не очищался.

| Прогон | Вход | Parser | max_wal_size / wal_buffers | Запись | Скорость входа | Повтор PUT |
| --- | ---: | --- | --- | ---: | ---: | ---: |
| [A](benchmarks/results/2026-11-09-baseline-a-5gib.json) | 5 ГиБ | исходный | 1 ГиБ / 4 МиБ | 170,371 с | 30,052 МиБ/с | 29,363 с |
| [B](benchmarks/results/2026-11-09-wal8-only-b-5gib.json) | 5 ГиБ | исходный | 8 ГиБ / 4 МиБ | 133,426 с | 38,373 МиБ/с | 28,802 с |
| [C](benchmarks/results/2026-11-09-walbuffers16-c-5gib.json) | 5 ГиБ | исходный | 8 ГиБ / 16 МиБ | 74,391 с | 68,826 МиБ/с | 29,049 с |
| [F](benchmarks/results/2026-11-09-optimized-f-repeat-5gib.json) | 5 ГиБ | быстрый | 8 ГиБ / 16 МиБ | 64,762 с | 79,059 МиБ/с | 15,306 с |
| [E](benchmarks/results/2026-11-09-optimized-e-1gib.json) | 1 ГиБ | быстрый | 8 ГиБ / 16 МиБ | 13,973 с | 73,282 МиБ/с | 2,872 с |

В этой серии итоговые 5 ГиБ быстрее A в 2,63 раза; снижения скорости относительно
итоговых 1 ГиБ не наблюдалось. Это отдельные последовательные прогоны, а не средние
значения или доверительные интервалы. Случайный payload, локальный диск, кеш и
конкуренция за одну машину ограничивают переносимость результата.

### Что ограничивало запись

- В A 203 из 335 наблюдений API-backend были `active / IO / WALWrite` — около 61%.
  Число запрошенных checkpoint в окне наблюдения A/B снизилось с 11 до 1 при
  увеличении max_wal_size. Это согласуется с дополнительной нагрузкой от частых
  checkpoint. Объём сгенерированного WAL почти не изменился — около 5,69 ГиБ.
- Увеличение wal_buffers отдельно от max_wal_size (B → C) уменьшило
  `wal_buffers_full` с 576 839 до 148 489, `wal_write` с 577 674 до 149 019,
  `wal_write_time` с 78,226 до 21,288 с. Это подтверждает пользу большего буфера
  WAL на этом стенде. В F число WAL writes — 209 007, время — 24,743 с:
  давление WAL снизилось, но запись журнала остаётся заметной работой.
- В Python каждая строка проходила regex-поиск NUL и суррогатов. Для ASCII теперь
  используется быстрая проверка NUL и `isascii()`, для остальных строк сохраняется
  исходный поиск. Ошибочные строки, ключи, Unicode, digest и счётчики проверены
  регрессионными тестами. Разницу C → F нельзя полностью приписать парсеру из-за
  разброса I/O; повтор PUT, который проверяет поток без нового COPY, ускорился
  с 29,049 до 15,306 с.

Счётчики WAL/bgwriter относятся ко всему кластеру и включают фоновую работу.
Их окно шире HTTP PUT: подключение/остановка монитора и пауза публикации статистики.
Времена WAL/checkpoint нельзя складывать как независимые части времени запроса;
checkpoint_write_time включает намеренно растянутую фоновую запись.
Наблюдение `active / none / none` само по себе не доказывает загрузку CPU.
`wal_sync=0` здесь не означает отсутствие синхронизации: используется
`wal_sync_method=open_datasync`. Метод синхронизации не менялся ради ускорения.
В исходных замерах 2026-11-08 этих счётчиков не было: точную долю причин старого
разрыва 1/5 ГиБ восстановить нельзя.

### Проверка замеров и результата

Прогон [D](benchmarks/results/2026-11-09-optimized-d-5gib.json) исключён из сравнения
производительности: клиентский таймер показал 69,244 с, PostgreSQL — 245,004 с
активного времени и 205,145 с WAL I/O. Данные прошли проверку, но причина расхождения
длительностей не установлена; значения не корректировались. На macOS часы Python
и PostgreSQL могут по-разному учитывать системный сон
([Apple](https://developer.apple.com/documentation/kernel/1646199-mach_continuous_time?language=objc),
[PG14 timer](https://github.com/postgres/postgres/blob/REL_14_20/src/include/portability/instr_time.h));
это возможное объяснение, а не доказательство события D.

F повторён с `caffeinate -i` и сопоставлением двух таймеров: обычный — 64,762977 с,
монотонный — 64,761865 с, разница 0,001112 с. Активное время БД — 64,785 с.
Полнота activity-monitor B/C/D/E/F — complete, без timeout/ошибок. Первый неудачный
запуск B завершился HTTP 201, но ошибка диагностического монитора прервала дальнейшую
проверку; он не включён в результаты. Обработка ошибок монитора исправлена перед
повтором B. Версии диагностической обвязки и их границы описаны в
[benchmarks/README.md](benchmarks/README.md#диагностика).

SHA-256 исходников в JSON относятся к файлам, исполненным во время замеров,
до добавления поясняющих комментариев; алгоритм после замеров не менялся.

Для всех шести сохранённых прогонов проверены receipt/GET, полное чтение **каждой**
строки с проверкой общего SHA-256, полный повтор PUT без дубликатов, receipt и число строк после
штатного перезапуска PostgreSQL/API. Итоговый RSS API: 70,03 МиБ на 1 ГиБ и
70,81 МиБ на 5 ГиБ; на 5 ГиБ клиент — 58,17 МиБ, отдельный backend — 176,77 МиБ.
Это выборки раз в 0,5 с, а не гарантия максимума памяти. Схема, индексы, FK,
одна транзакция и гарантии commit сохранены. Нагрузочные базы удалены,
временный PostgreSQL остановлен.

После изменений прошли 137 unit/fault-тестов и 12 тестов с настоящим PostgreSQL,
Ruff check/format, строгая валидация OpenSpec и проверка diff. В runtime не добавлены
зависимости. Сборка/запуск Compose локально не проверены: Docker daemon недоступен.

Опциональный [compose.bulk.yaml](compose.bulk.yaml) задаёт 8 ГиБ WAL и буфер 16 МиБ.
Для внешнего PostgreSQL параметры задаёт администратор; приложение их не меняет.
Больший max_wal_size требует дискового запаса и может увеличить crash recovery;
это мягкий предел, а реплики/архиватор могут удерживать дополнительный WAL.
Основание: [bulk loading](https://www.postgresql.org/docs/14/populate.html#POPULATE-MAX-WAL-SIZE),
[WAL configuration](https://www.postgresql.org/docs/14/wal-configuration.html) и
[параметры WAL](https://www.postgresql.org/docs/14/runtime-config-wal.html).
Профиль PostgreSQL 17 в Compose, реальные результаты калькуляции, TLS, репликация,
одновременные загрузки и аварийное восстановление требуют проверки на целевом стенде.

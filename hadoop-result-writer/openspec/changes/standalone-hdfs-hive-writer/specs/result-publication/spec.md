## Purpose

Сохранять результат одного расчёта с ограниченным потреблением памяти двумя способами: напрямую в HDFS и SQL-записью через Trino, с явной фиксацией результата.

## ADDED Requirements

### Requirement: Потоковая запись
Пакет SHALL принимать последовательность Arrow RecordBatch с фиксированной схемой и MUST NOT материализовывать весь результат. Пустой поток SHALL отклоняться явно.

#### Scenario: Большой результат HDFS
- **WHEN** передан поток 1–5 ГБ в режиме hdfs
- **THEN** Parquet-файлы загружаются последовательно, память ограничена порцией/writer, локальный диск — текущим файлом

### Requirement: Python input
Оба режима SHALL принимать pandas DataFrame, Arrow Table/RecordBatch и поток словарей Python через общий адаптер. Пакет SHALL поддерживать явную pyarrow.Schema и безопасные преобразования, MUST NOT молча отбрасывать колонки. Для словарей схема MUST быть обязательной. Конвертация DataFrame SHALL идти порциями без сохранения индекса.

#### Scenario: DataFrame с явной схемой
- **WHEN** передан DataFrame и pyarrow.Schema
- **THEN** оба режима сохраняют заданные типы, отклоняют переполнение и не материализуют вторую полную Arrow-копию

#### Scenario: Ленивые Python records
- **WHEN** передан генератор словарей с явной схемой
- **THEN** генератор читается порциями с ограничением числа строк, лишние ключи отклоняются

### Requirement: HDFS commit
HDFS-режим SHALL фиксировать result_id только после закрытия всех файлов и manifest. Commit MUST быть атомарным и не перезаписывать существующий результат. Успех означает сохранение в HDFS, без обещания регистрации Hive.

#### Scenario: Сбой до commit
- **WHEN** загрузка обрывается до атомарной фиксации
- **THEN** lookup не возвращает подтверждённый результат, незавершённые данные не публикуются потребителям commit-протокола

### Requirement: SQL публикация
Trino-режим SHALL выполнять SQL-запись в таблицу попытки и публиковать итоговое имя только после завершения записи и проверки строк. Неопределённый INSERT MUST NOT повторяться автоматически.

#### Scenario: Прерванный INSERT
- **WHEN** ответ SQL INSERT потерян
- **THEN** попытка остаётся под промежуточным именем без публикации итоговой таблицы

### Requirement: Повтор и конфликт
Оба режима SHALL предоставлять lookup без генерации данных, распознавать повтор с тем же fingerprint и отклонять различающееся содержимое без перезаписи. Контракт fingerprints MUST быть документирован.

#### Scenario: Повторная публикация
- **WHEN** тот же result_id публикуется с совпадающим fingerprint
- **THEN** возвращается уже существующий receipt без дублирования итогового результата

#### Scenario: Различающееся содержимое
- **WHEN** result_id уже опубликован с другим fingerprint
- **THEN** пакет возвращает конфликт и сохраняет существующий результат

### Requirement: Неопределённый исход
После ошибки финальной фиксации пакет MUST сверить фактическое состояние и SHALL различать успех, конфликт и неопределённый исход. Невозможность проверки MUST NOT трактоваться как отсутствие результата.

#### Scenario: Ответ commit потерян
- **WHEN** фиксация выполнена, но ответ не получен
- **THEN** readback возвращает подтверждённый receipt либо явную ошибку неопределённого исхода без удаления данных

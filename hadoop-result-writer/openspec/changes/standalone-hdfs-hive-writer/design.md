## Context

Данные расчёта 1–5 ГБ, хранилище HDFS, чтение через Trino/Hive. По уточнению пользователя нужны две версии записи. Параметры реального KDC и кластера отсутствуют. См. proposal.md.

## Goals / Non-Goals

**Goals:** один устанавливаемый пакет, два режима, Kerberos, контейнер, демонстрация и проверяемые отказы.

**Non-Goals:** общий commit HDFS + Hive, несколько таблиц в одной транзакции, обновление опубликованного результата, автоматическая интеграция с Kafka.

## Decisions

### Общий API

`Connection(Config(...))` управляет Kerberos. `connection.writer.publish(result_id, batches)` принимает итератор Arrow RecordBatch, а `lookup(result_id)` проверяет подтверждённую публикацию без повторной генерации данных. Receipts возвращают пути/таблицы, счётчики и fingerprint. Режим выбирается до подключения.

### Kerberos

`kinit -kt` получает TGT в приватный FILE-кеш. Фоновая задача повторяет получение из keytab, каждый вызов клиента проверяет credentials, ошибка обновления блокирует операции. KRB5_CONFIG задаётся окружением процесса до запуска. Hadoop XML и keytab монтируются снаружи. Trino получает GSSAPI credentials из явно заданного кеша, требует HTTPS и mutual authentication; SQL-соединение пересоздаётся на запрос. Ошибки subprocess/SQL не раскрывают ответ сервера и секреты.

### Режим HDFS

Hadoop CLI наследует Kerberos-кеш и настройки HA. В памяти находится текущая Arrow-порция, локально — текущий Parquet-файл. Ротация по 256 МиБ несжатых данных; размер после сжатия не гарантируется. Файлы последовательно загружаются в `staging/<uuid>`. Manifest содержит schema fingerprint, SHA-256, размеры и строки файлов. Пустой результат отклоняется.

Закрытый каталог перемещается в уникальный `results/<uuid>`. Маленький закрытый commit-файл перемещается в `_commits/<result_id>.json` без перезаписи: это точка фиксации. Конкурирующие попытки согласуются существованием единственного commit-файла. По ошибке rename читается фактический commit. Читатели должны использовать commit/receipt, а не рекурсивно читать `results/`: там могут остаться неопубликованные попытки. HDFS CLI `-mv` не должен перезаписывать существующий файл; интеграционный тест проверяет эту предпосылку. Использование разных HDFS/encryption zones для rename не поддерживается.

Lookup проверяет digest manifest и размеры файлов. За передачу байтов отвечают проверки HDFS; SHA-256 Parquet записан для независимой глубокой проверки, но lookup не перечитывает гигабайты. Повтор publish сравнивает физические manifests: смена порций, компрессии или версии Parquet может дать конфликт для логически тех же строк. Для повтора после сбоя вызывается lookup. Команда diagnose проверяет подключение без записи, но не доказывает право публикации.

### Режим Trino

Пакет использует только SQL Trino. Создаёт внешнюю непартиционированную Parquet-таблицу с уникальным именем `_hrw_<uuid>` в настроенной тестовой схеме и отдельным HDFS location. Ограниченные SQL INSERT передают Python-строки, schema и значения проверяются и экранируются. На один INSERT — около 128 КиБ SQL-значений; строка больше этого лимита отклоняется. После всех INSERT проверяется количество строк. В comment сохраняются result_id, location, строки и fingerprint потока. Финальная публикация — `ALTER TABLE ... RENAME TO <prefix>_<hash(result_id)>`, затем readback. Метаданные и row count проверяются lookup.

Неопределённый INSERT никогда автоматически не повторяется: попытка остаётся под приватным именем. Повтор начинает новую таблицу. Приватность имени — соглашение потребителей, не ACL; права и отдельная схема ограничивают доступ. Rename должен быть атомарным и не перезаписывать таблицу в выбранном Hive Metastore. Эту предпосылку проверяют интеграционные тесты целевого Trino. HDFS-режим не зависит от неё.

SQL INSERT удобен для демонстрации, но для 1–5 ГБ означает много запросов и маленьких файлов. Он не объявляется готовым высокопроизводительным каналом; для production потребуется измерить его и, вероятно, заменить загрузку на staging/INSERT SELECT или CTAS, сохранив публикацию. Этот прототип не переименовывает данные внутри общей существующей таблицы.

### Контейнер и стенд

Один образ содержит Python, Java, Hadoop client и Kerberos utilities. Код не запаковывается PyInstaller. Работает UID 10001 с read-only root и tmpfs для кеша/текущего файла. Локальная демонстрация использует реальный Parquet и файловую фиксацию, без симуляции авторизации или репликации. Контейнерный стенд проверяет MIT KDC и защищённый HDFS. Trino-путь тестируется управляемым SQL-адаптером; реальный Trino требует отдельного приёмочного прогона, явно отмеченного в tasks/report.

## Risks / Trade-offs

- Commit в HDFS не регистрирует таблицу Hive и не гарантирует видимость в Trino → отдельный этап интеграции потребителя.
- Потеря ответа commit/rename → возвращать неопределённый исход, сохранять попытки, повторять lookup.
- Незавершённые и проигравшие попытки занимают место → сохранять для диагностики; автоматическое удаление не входит в прототип.
- HDFS lookup перечисляет каталог commit-файлов → для большого числа результатов потребуется индекс/разбиение по префиксам.
- SQL fingerprints зависят от schema metadata и порядка строк; HDFS дополнительно от физического разбиения → явно документировать контракт повторов.
- Особенности настоящих KDC/ACL/SASL/HA и транзакционности rename → не обещать production-гарантии без приёмки.

## Migration Plan

Демонстрация в отдельном каталоге, сборка образа, тестовый KDC/HDFS, затем проверка в отдельной схеме целевого Trino. Основной worker подключать отдельным изменением после сравнения результатов. Откат — остановка прототипа; production-данные он не удаляет и не изменяет.

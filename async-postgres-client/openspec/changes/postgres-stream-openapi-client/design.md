## Context

Существующий сервис хранит подтверждённые загрузки, предоставляет чтение страниц
и отдаёт NDJSON порциями до 128 КиБ. Порция отправки не равна строке NDJSON и не задаёт
размер порции на стороне клиента. OpenAPI описывает интерфейс, а корректность обмена
потоками дополнительно проверяется по фактическим HTTP-ответам.

## Goals / Non-Goals

Один устанавливаемый асинхронный Python-клиент для записи, выборочного чтения
и полной выгрузки. Синхронный API, встроенный доступ к БД, автоматическое
возобновление потока, CLI и изменение сервера не входят в изменение.

## Decisions

1. Источник контракта — `async-postgres-writer/openapi/stream-writer.v1.yaml`,
   который добавляет изменение `postgres-stream-openapi-server`. Для клиента
   фиксируем ревизию контракта и проверяем его в CI. Если YAML включён в сборку,
   он копируется из этого источника; второго редактируемого контракта нет.
   Разработку клиента можно начать с тестового HTTP-транспорта; для проверки
   совместимости перед выпуском нужны серверный артефакт и запущенный сервис.
2. Публичные методы `upload_ndjson`, `get_upload_receipt`, `list_upload_rows` и
   `stream_upload_rows` соответствуют операциям `uploadNdjson`, `getUploadReceipt`,
   `listUploadRows` и `streamUploadRows`. Для четырёх операций достаточно небольшого
   адаптера поверх переиспользуемого `httpx.AsyncClient`; CI сверяет адаптер с контрактом.
   Генерация обычных JSON-методов допустима позже, если сохраняет точные числа.
   Потоки реализуем явно:
   [запросы](https://www.python-httpx.org/async/#streaming-requests),
   [ответы](https://www.python-httpx.org/async/#streaming-responses).
3. Клиент создаётся с URL, Bearer token и настраиваемыми таймаутами HTTP; TLS
   проверяется по умолчанию. `async with` управляет HTTP-пулом и отдельно временем
   жизни потокового ответа. Ошибки HTTP сохраняют статус и доступные `error/message`
   или `detail`; неизвестный формат ошибки также обрабатывается без чтения
   неограниченного тела. Транспортные и протокольные ошибки различаются.
4. PUT передаёт итератор байтов без пересериализации и без автоматического replay.
   Отправитель заранее сохраняет UUID и способ заново получить те же байты. При
   неопределённом исходе он проверяет квитанцию по этому UUID. `404` при проверке
   не исключает выполняющийся PUT. Явный повтор допустим с тем же UUID и теми же
   байтами; SHA-256 квитанции относится к PUT, его нельзя сверять с выгрузкой JSONB.
5. Постраничное чтение передаёт только один из параметров позиции; для курсора
   последовательность начинается с `after_row_number=0`, далее передаётся
   `next_after_row_number` до `null`. Произвольные числа JSON декодируются
   без промежуточного `float`: целые в `int`, дробные и экспоненты в `Decimal`.
6. Выгрузка проверяет тип ответа и `X-Row-Count` до выдачи первой записи. Парсер
   находит LF в байтах, декодирует UTF-8 после сборки строки и применяет настраиваемый
   лимит байтов на строку ответа. Лимит учитывает обёртку и представление JSONB,
   поэтому не выводится из ограничения строки PUT или 128 КиБ. Полнота подтверждается
   только после штатного EOF, когда последняя строка закрыта LF, а счётчик совпал.
   Уже выданные строки остаются предварительными до этой проверки. Закрытие ответа
   при выходе из контекста, ошибке или отмене освобождает ресурсы; досрочный выход
   не подтверждает результат.

## Risks / Trade-offs

- Потребитель должен сам отложить публикацию выгрузки до нормального завершения
  потока. Пример записи в файл использует временный файл и переименовывает его
  только после успешного окончания проверки.
- Медленный читатель дольше удерживает соединение на сервере. Ограничение числа
  одновременных выгрузок остаётся ответственностью вызывающего приложения.
